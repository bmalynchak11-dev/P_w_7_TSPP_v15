# Відповіді на питання

### 1. Які три ризики вашого реєстру найважливіші і за якими числами (оцінка, очікувана вартість) ви це визначили?
У реєстрі проєкту найважливішими є такі три ризики:
1. **R-01** (Збої транзакцій через API платіжного шлюзу):
   - Оцінка пріоритету: `score = 16` ($p=4, i=4$, зона «висока»).
   - Очікувані грошові втрати: `EMV = 24 000.0 грн` ($pct = 60\%$, $loss = 40 000$ грн).
2. **R-02** (Блокування таблиць БД через навантаження під час імпорту):
   - Оцінка пріоритету: `score = 12` ($p=3, i=4$, зона «висока»).
   - Очікувані грошові втрати: `EMV = 12 000.0 грн` ($pct = 40\%$, $loss = 30 000$ грн).
3. **R-03** (Втрата актуальних бекапів через відмову сервера):
   - Оцінка пріоритету: `score = 10` ($p=2, i=5$, зона «висока»).
   - Очікувані грошові втрати: `EMV = 10 000.0 грн` ($pct = 20\%$, $loss = 50 000$ грн).

### 2. Чому для найважливішого ризику обрано саме цю стратегію і що лишилося після реагування?
Для ризику **R-01** обрано стратегію **«зниження» (мітигація)** за правилом T4.
* **Чому обрано:** Ризик належить до високої зони, не є організаційним (scope != 'org') та не може бути повністю усунений уникненням без відмови від платіжного функціоналу. При цьому вартість розробки адаптера й проведення стендового тестування складає `6 000 грн`, що суттєво менше за очікувані втрати `EMV = 24 000 грн` ($mitigate\_cost < EMV$). Економічно та технологічно захід є високоефективним.
* **Залишковий ризик:** Після розробки адаптера та тестування ймовірність збою знижується з $p=4$ до $p_{after}=2$, а тяжкість наслідків — з $i=4$ до $i_{after}=3$. Залишковий бал складає `residual_score = 6`, що переводить ризик у допустиму для проєкту зону «середня» ($score \le 9 \le tolerance$).

### 3. Як ви обрали тригер для одного з ризиків і хто, крім власника, має дізнатися про його спрацювання?
* **Ризик:** **R-02** (високе навантаження на БД і блокування таблиць).
* **Вибір тригера:** Метрика `db_slow_queries_count >= 15` (кількість запитів, виконання яких триває понад 1 секунду за годину). Це чітко вимірюваний технічний показник сервісного моніторингу APM/PostgreSQL, який сигналізує про деградацію продуктивності ще до того, як інтерфейс повністю зависне для кінцевого користувача.
* **Коло сповіщення:** Окрім безпосереднього власника ризику (провідного бекенд-розробника Олександра Шевченка), сповіщення має автоматично надходити в загальний канал сповіщень команди розробки (DevOps/SRE інженеру для масштабування ресурсів) та скрам-майстру/тімліду для оперативного коригування черги задач.

### Рецензування (зауваження до реєстру колеги)
Під час взаємного аудиту реєстру колеги виявлено такі зауваження:
1. **Невимірюваний тригер у формулюванні:** У ризику колеги щодо зриву дедлайнів тригер було записано як «команда не встигає». Запропоновано замінити на числову вимірювану метрику, наприклад: `sprint_velocity_drop_pct > 25` або `unresolved_blocking_tasks >= 3`.
2. **Невідповідність стратегії та зони:** Для ризику критичної зони ($score = 20$) було призначено пасивне прийняття без виділення резерву чи плану мітигації, що суперечить правилу `rule_response`. Рекомендовано змінити стратегію на «зниження» або «ескалація».
